## 这个项目干什么

**从画面里认出右手 5 根手指各自的「伸开 / 蜷起」**，用于驱动机械手。

```
输出 = [拇指, 食指, 中指, 无名指, 小指]    每个是 伸开 / 蜷起
```

> ### 为什么不做"手势分类"（认 0~9）？
>
> 因为机械手要模仿的是**具体哪几根手指伸开**。
> 比如"三指"这个数字有中西两种比法（食+中+无名 / 拇+食+中），
> **对机械手来说是两个不同的动作** —— 光输出一个"3"没有用。
>
> 所以本项目**直接输出 5 位手指状态，不再输出数字标签**。

全部算法手写：YCbCr 色度阈值分割、场景色度自校准、颜色约束重建、距离变换找掌心与手掌尺度（当作量长度的尺子）、轮廓剖面与凸出长度找指尖、指缝定位、三判据打分定手指身份。

## 算法怎么工作的

整体是一条**逐层收紧的漏斗**，每层都能用 `1`~`6` 单独看：

```
① 载入降采样     照片按 2560×1440 压一次；视频/摄像头按长边 1280 压
      ↓
② 框出 ROI       只看画面中间一块（宽度按**短边**算，竖幅不会塌）
      ↓
③ 颜色阈值       「像皮肤」→ 白。★ 先做场景色度自校准
      ↓
④ 掩膜清理       小核开运算 + 双门槛面积过滤 + 只填内部孔洞
      ↓
⑤ 掌心重建       从掌心核心做颜色约束重建（连通的允许区）
      ↓
⑥ 找手掌 C 和 R  C = 距离变换最大值点，R = 那个最大值（**当作量长度的尺子**）
      ↓
⑦ 截前臂         找手腕（横截面最窄行）→ 切掉掌心下方 1.5R 以外
      ↓
⑧ 找指尖 / 指缝  指尖用「凸出长度」判据；指缝是轮廓上的凹谷
      ↓
⑨ ★ 手指身份识别  三个独立判据打分，判断每根手指伸/缩
      ↓
⑩ ★ 稳定性门控    手在动就不更新输出
```

### 几个关键设计

#### ① 场景色度自校准（换光照不用改参数）

`CR_LOW=131 / CB_HIGH=128` 这类**写死的绝对阈值**在换光照后会整体失效 —— 而且**调数值救不回来**（实测把下限从 131 抬到 152，最差那批从 4/10 掉到 1/10）。

正确做法是**把整个肤色框按本帧估计的平移量一起挪**：光照整体变化时，背景和肤色的色度是**一起平移**的，按同一位移平移肤色框，"背景在框外、手在框内"这个相对关系就恢复了。

平移量从 **ROI 内 Cr/Cb 的中位数**估计（背景占大头 → 中位数 ≈ 背景色）：

| 场景 | 偏移量 |
|---|---|
| 白板（标定基准）| `+0 / +0` |
| 斑驳桌面 | `+1 / -2` |
| **印花床单 + 暗暖光** | **`+6 / -7`** ← 这一层把原始前景占比从 **41.8% 压到 18.0%** |

> ⚠️ 故意**不用**"当前掩膜之外的像素"估背景 —— 那是循环论证：阈值已经糊掉时，被排除的只剩最亮的部分，估出来的平移方向是**反的**。

#### ② 自适应 ROI

旧做法宽度按**画面宽度**算 → 竖幅 810×1440 时 ROI 只有 **406 px**，**整个拇指落在框外被擦黑**。
改成按**画面短边**算后宽度变成 **608 px**。

#### ③ 掌心估计的稳健化

掩膜偶尔会被颜色筛选割出一道口子，最大内切圆只塞进半块掌 → **R 被严重低估**（实测某张算出 101.5，按手掌实际大小应约 163）。

修法：**闭运算只作用在一份副本上、专门用来估掌心**，找指尖仍用原始掩膜（指缝一点没糊）。
核边长按**掩膜面积**算而不按 R 算 —— 按 R 算会陷入鸡生蛋（R 本身就是被低估的那个量）。

效果：那张 R 从 101.5 修正到 **162.6（+60%）**，其余 19 张变化都在 −4.8% ~ +0.9%。

#### ④ ★ 手指身份识别：三个独立判据

难点不在"有没有东西伸出来"，而在**"伸出来的是哪一根"**。

**为什么不能只看角度**：同一根手指在**不同姿势**下的角度漂移有 **30~40°**，
而相邻手指的名义间隔只有 **17.5°** —— 光靠"绕掌心的角度"分不出食指/中指/无名指。

所以用三个**互相独立**的判据一起打分：

| 判据 | 说明 |
|---|---|
| **① 指尖角度 + 拇指锚定** | 拇指实测角度 `+46°~+82°`，其余四根都在 `+30°` 以下 —— **有干净间隔**，所以"最大角 > 40°"能可靠认出拇指。认出后把整个模板对齐过去，角度歧义就消失了 |
| **② 指尖长度** | 解剖学固定：**拇指明显最短**（2.18R）、**中指最长**（3.00R）、**小指在非拇指里最短**（2.54R）|
| **③ 指缝的横向位置** | ★ 指缝离掌心只有 1.1~1.3R，指尖在 2.7~3.0R —— **同样的角度误差，换算成横向位置时在指缝处小 2.4 倍** |

**判据③最值得一提**。实测四条指缝的名义位置（单位 R，掌心为 0，正方向 = 拇指侧）：

| 指缝 | 名义位置 | 范围 |
|---|---|---|
| **T-I（拇指-食指）** | **+0.72** | +0.53 ~ +1.00 |
| I-M | +0.20 | −0.32 ~ +0.48 |
| M-R | −0.34 | −0.80 ~ −0.05 |
| R-P | −0.84 | −1.17 ~ −0.53 |

其中 **T-I 缝（最低 +0.53）和 I-M 缝（最高 +0.48）几乎不重叠** ——
这直接印证了"**拇指的指根离手腕最近**"这个解剖学事实，也成了区分拇指最有力的证据。

#### ⑤ 稳定性门控

> 实测观察：**手在摆造型的过渡帧**容易判错，**手摆好不动的帧**基本能认对。

在 ROI 内**隔点采样缩到 64×64 灰度**，与上一帧比平均绝对差 = 运动量：

- 运动量 ≤ 2.0 算"稳"，连续 3 帧稳 → 认为手摆好了，记下这一帧的判定
- 手没摆好 → 输出**保持上一次稳定时的判定**，方块套黄色虚线框提示

实测：保持姿势的帧运动量 **0.3~0.9**，真正的过渡帧 **1.8~4.0**，门槛 2.0 分得开；
保持姿势时 41 帧里有 **39 帧**判定为"稳"。

## 参数与调参

### 输入源（`main.py` 开头）

```python
SOURCE     = "video"                 # image / video / camera（命令行可覆盖）
VIDEO_FILE = "gesture_video_1.mp4"   # 相对 DATA_DIR
DATA_DIR   = "data"                  # 素材子目录（"" = 和代码同目录）
MIRROR_DEFAULT      = False          # ★ 右手项目，绝不自动镜像
VIDEO_MAX_LONG_SIDE = 1280           # ★ 视频/摄像头帧长边上限（0 = 不限制）
IMAGE_MAX_WIDTH/HEIGHT = 2560/1440   # 只作用于**照片**载入时
```

> ⚠️ `VIDEO_MAX_LONG_SIDE` 很关键：照片的降采样只在载入时做，
> **视频/摄像头这条路径以前完全不经过它** —— 1080×1920 的视频是整幅 2.07 Mpx 进流水线的。
> 加上限制后 **181 ms → 57 ms（3 倍）**。
> 瓶颈是占 **62%** 的 `palm_reconstruct`，它按像素数线性涨。

### 算法参数（`plugins.py`，分七个部分）

| 部分 | 关键常量 |
|---|---|
| 一 ROI | `ROI_WIDTH_VS_SHORT=0.75`、`ROI_HEIGHT_RATIO=0.80`、`ROI_AUTO_TRACK=False` |
| 三 颜色 | `CR_LOW/HIGH=131/173`、`CB_LOW/HIGH=77/128`、`SCENE_CALIBRATE=True` |
| 四 清理 | `CLEANUP_OPEN_KERNEL=3`、双门槛面积过滤 |
| 五 重建 | `RECON_PALM_CLOSE_RATIO=0.13`（**核按面积算，不按 R 算**）|
| 六 识别 | `RECOG_TIP_PROTRUSION_MIN=1.45`（凸出长度，主力判据）|
| **七 手指** | `FINGER_TEMPLATE_DEG`、`FINGER_TEMPLATE_LEN`、`FINGER_WEB_X`、四个权重 |
| 门控 | `STABLE_DIFF_MAX=2.0`、`STABLE_MIN_FRAMES=3` |

**手感速查**：

- **ROI 太紧、手被切** → 调大 `ROI_WIDTH_VS_SHORT`，或运行时按 `r` 直接关掉 ROI
- **掩膜糊成一片** → 看左下角的 `foreground %`，**超过 25% 基本就是糊了**；抬高 `CR_LOW`
- **手在动时方块跳** → 调大 `STABLE_DIFF_MAX`（更宽松）或 `STABLE_MIN_FRAMES`（更迟滞）

## 已知限制（**如实说明**）

这个项目在**当前这批素材**上工作良好，但下面几条是实测确认的短板：

### ① 参数是在一批素材上标定的，不是推导出来的

约 **15 个自由参数 / 25 张样本**，而且**两次"更讲道理、零魔法数字"的改动都让准确率下降**：

| 改动 | 客观指标 | 结果 |
|---|---|---|
| 用前臂主轴估掌轴 | 中指对准掌轴的标准差 12.4° → **7.7°**（更准 ✓）| **24 → 19** ✗ |
| 两个手性假设比代价 | 纯模型选择，零阈值 ✓ | **24 → 19** ✗ |

**所以 24/28 不能证明泛化能力。** 换人、换相机、换光照都不保证。
→ 真正的解法是**开机自标定**（让用户张一次手、伸一次掌，现场学模板和颜色阈值），**还没做**。

### ② 手背朝镜头会左右镜像

`gesture_33` 那三张是**手背朝镜头**拍的，实测角度**全是负的**，和掌心朝镜头的样本正好相反 ——
而模板是按"掌心朝镜头"标定的，所以这三张会被判反（拇指 ↔ 小指）。

**当前约定：右手 + 掌心朝镜头。**

### ③ 暗光 + 背景撞色时会糊

实测某段视频（暗暖光 + 印花床单）里，床单的**粉色印花在暗光下整体进入肤色范围**：

| | Cr | **Y（亮度）** |
|---|---|---|
| 印花块 | 147 ~ 155 | **134 ~ 157（亮）** |
| 手块 | 157 ~ 159 | **71 ~ 115（暗）** |

**Cr 上几乎完全重合，只有亮度 Y 能分。**
而现在的 `Y` 区间是 `[40, 245]`，**等于完全没用上这条线索** ✗
（实测"手比背景暗"在**所有样本**上成立：低 19~99）

### ④ 性能瓶颈明确

`palm_reconstruct` 一层占 **62%** 的时间，而它做在整幅图上 ——
其实只需要在手附近做，**还有约一倍空间**。

## 目录结构

```
.
├── main.py        流水线骨架：输入 → 插件链 → 显示
├── plugins.py     全部图像算法，分七个部分
├── README.md
└── data/          素材目录（**不在仓库里**，见下）
```

### 关于 `data/`

`data/` 被 `.gitignore` 忽略 —— **素材不随仓库上传**（几十 MB 的图片和视频）。
仓库里的 `data` 是一个 **Windows 目录联接**，指向开发目录的素材，这样仓库副本能直接跑而不用改一行代码。

要用自己的素材：在**代码同级**建一个 `data/` 目录，把图片/视频放进去，并在 `main.py` 的
`GESTURE_SAMPLES` 里登记文件名即可（把 `DATA_DIR` 改成 `""` 就退回"素材和代码同目录"）。

### 插件机制

处理逻辑全部是**插件**，契约很简单：

```python
def my_step(frame: np.ndarray, state: FrameState) -> Optional[np.ndarray]:
    """
    frame : 插件工作帧（是一份拷贝，可放心就地修改）
    state : 本帧共享状态
    返回 None 表示丢弃本帧
    """
```

在 `plugins.py` 的 `register(api)` 里 `api.add("名字", 函数, enabled=True)` 就接进去了，
**主程序一行都不用改**。注册顺序 = 执行顺序（**处理类在前、绘制类在后**，否则画的标注会被后续的二值化吃掉）。

## 技术约束

- **不能用深度学习**（不用 CNN / MediaPipe / `cv2.dnn` / torch / tf / 云端）
- **不用 `opencv-contrib-python`**
- **不用背景差分**（后面要换背景测试）
- 只处理**右手**，**绝不自动镜像**
