# OpenCV Hand Gesture Recognition

**纯传统计算机视觉（classical computer vision）的手势识别 —— 不依赖 CNN、MediaPipe、任何深度学习运行时或云端服务。**

全部算法只用 `opencv-python` + `numpy` + Python 标准库手写：YCbCr 色度阈值分割、颜色约束重建、距离变换找掌心与手掌尺度、轮廓距离剖面找指尖、多尺度曲率、凸缺陷、骨架细化、几何特征分类、滑动窗口时序投票。

### 现在能做什么

| 路线 | 能力 |
|---|---|
| **A：`main.py` + `plugins.py`** | 分割 → 定位掌心/手腕 → 找指尖/指缝 → **分类出中国式数字手势 `0 / 1 / 2 / 3 / 4 / 5 / 6 / 8`**。在 **20 张实测素材（两种背景、两档拍摄距离）上 20/20 全对**。不需要标定。 |
| **B：`solution.py`** | 早期成品，走"背景差分 + 肤色马氏距离"路线，只识别**数字 5**，需要一次性标定。留作对照与参考。 |

> 分类结果**完全由图像计算得出**，代码里没有任何"按文件名/按张号查表"的映射 —— 详见[手势分类](#手势分类路线-a)。

## 项目定位与能力边界

**先说实话，避免误解：**

| 项目名说的是 | 实际目前做到的 |
|---|---|
| Hand Gesture Recognition（手势识别） | **路线 A 能判出数字 0/1/2/3/4/5/6/8 共 8 个手势**；路线 B 只识别数字 5 |
| 通用手势库 | 路线 A 有 8 类；不认的手势会输出 `?`（未知）而不是乱猜 |
| 开箱即用 | 不是。需要自备图片素材，或改用摄像头模式 |

- ✅ **路线 A 分类目标**：中国式数字手势 `0`(握拳) `1` `2`(剪刀) `3` `4` `5`(五指张开) `6`(点赞/只伸拇指) `8`(手枪/拇指+食指)
- ✅ **`3` 的两种比法会自动归为一类**：`食指+中指+无名指` 和 `拇指+食指+中指` 都判为 `3`（原理见[手势分类](#手势分类路线-a)）
- ✅ 极端轻量：无模型文件、无 GPU、无网络请求，CPU 实时
- ✅ 算法完全透明可调：每个阈值都有物理含义，且**带实测依据**（见[实测数据附录](#实测数据附录)）
- ⚠️ 路线 A **不需要标定**，但**面向固定室内场景**（干净/较杂背景均可，实测两种背景都对）
- ⚠️ 路线 B 需要一次性标定（空背景 + 肤色采样），只识别数字 5
- ⚠️ 每个手势目前**只有单张样本**，阈值虽已实测标定，但**还没做过跨角度/跨人的验证**

这是一个**算法研究与调参用**的仓库，不是开箱即用的通用手势识别 SDK。

## 两条实现路线怎么选

仓库里有**两条独立实现**，不是一套代码的两种入口：

| | **路线 A：`main.py` + `plugins.py`** | **路线 B：`solution.py`** |
|---|---|---|
| 定位 | 插件式**算法实验台** | 单文件**可运行成品** |
| 行数 | **994 + 1924** | 1881 |
| 输入 | 磁盘图片循环处理 **或** 2K 摄像头 **或** 视频文件 | 640×480 摄像头 |
| 分割策略 | **YCbCr 固定区间阈值 + 颜色约束重建** | **背景差分 + 马氏距离肤色模型** |
| 是否标定 | 不需要 | 需要（背景 30 帧 + 肤色 60 帧） |
| **识别能力** | **数字 0/1/2/3/4/5/6/8（8 类），实测 20/20** | 只识别数字 5（`FIVE` / `UNKNOWN`） |
| 分类依据 | 伸出手指**根数** + 每根手指**偏离掌轴的角度** | 5 指尖 + 4 指缝 + 实心度等 7 项加权 |
| 时序处理 | 无，逐帧独立（**这是目前最大的短板**） | **12 帧滑动窗口投票** |
| 交互 | 6 档递进显示模式、10+ 热键 | 分阶段引导 + `q` / `r` |
| 适合 | 调阈值、复盘、逐层看中间结果 | 演示、验收、端到端跑通 |

> **想调算法、想扩展手势用 A，想看一个端到端跑通的成品用 B。** 两者的分割思路不同，同一场景下的阈值**不能直接互抄**。
>
> A 的识别能力更强但**没有时序投票**（逐帧独立判定，上视频会跳）；B 有时序投票但只认一个手势。**下一步很自然的做法是把 B 的 12 帧投票搬到 A 上。**

## 快速开始

### ⚠️ 第一次运行 `main.py` 之前必读

本仓库**只提交代码，不提交图片素材**（素材是私人拍摄的照片）。而 `main.py` 默认走图片模式，`IMAGE_FILES` 由 `GESTURE_SAMPLES` 自动展平出 **18 个文件名**：

```python
SOURCE = "image"
GESTURE_SAMPLES = (
    (0,  "握拳",       ("gesture_00.jpg", "gesture_00_busy.jpg")),
    ...
)
```

**直接 `python main.py` 会打印"图片模式下一张可用图片都没有"并退出**（返回码 1）。三个办法任选：

**办法 1：改用摄像头模式（推荐先跑通这条）**

```python
# main.py 配置区
SOURCE = "camera"          # "image" / "camera" / "video"
```

```bash
python main.py
```

**办法 2：改用视频文件模式**

```python
SOURCE = "video"
VIDEO_FILE = "my_gesture.mp4"   # 相对 main.py 所在目录，也可写绝对路径
VIDEO_LOOP = True               # 播完循环；False = 播完自动退出
```

**办法 3：按下面的命名把图片放进仓库根目录**

命名规则是 `gesture_<两位数编号>[_busy].jpg`，`_busy` 后缀表示"背景更杂"的那一组：

| 编号 | 手势 | 需要的文件 |
|---|---|---|
| 0 | 握拳 | `gesture_00.jpg`、`gesture_00_busy.jpg` |
| 1 | 只伸食指 | `gesture_01.jpg`、`gesture_01_busy.jpg` |
| 2 | 食指+中指（剪刀） | `gesture_02.jpg`、`gesture_02_busy.jpg` |
| 3 | 三指（西式：食+中+无名） | `gesture_03.jpg`、`gesture_03_busy.jpg` |
| 4 | 四指 | `gesture_04.jpg`、`gesture_04_busy.jpg` |
| 5 | 五指张开 | `gesture_05.jpg`、`gesture_05_busy.jpg` |
| 6 | 点赞（只伸拇指） | `gesture_06.jpg`、`gesture_06_busy.jpg` |
| 8 | 手枪（拇指+食指） | `gesture_08.jpg`、`gesture_08_busy.jpg` |
| 33 | 三指（中式：拇+食+中） | `gesture_33.jpg`、`gesture_33_busy.jpg` |

> **`33` 那一项代表数字 `3`，不是数字 33。** 它和 `3` 是同一个数字的两种比法，分类器会自动归为一类（见[手势分类](#手势分类路线-a)）。
>
> 少放几张不会报错，`resolve_image_paths()` 会打印跳过哪些、继续跑剩下的。
> 图片会自动缩到 2K 以内（`IMAGE_MAX_WIDTH/HEIGHT`），**保持宽高比**，所以 4096×3072 的相机原图可以直接丢进来。

图片模式下会把**同一张图循环反复处理**，方便你一边看叠加结果一边按 `1`~`6` 切换中间层、按 `n`/`p` 换图、按 `r` 对比 ROI 开关效果。

### 运行 `solution.py`（完整成品）

```bash
python solution.py
```

按窗口提示分阶段操作：

1. `STAGE 0/3` 初始化，先把窗口开起来（摄像头慢时不会以为程序卡死）
2. `STAGE 1/3` 摄像头预热，丢弃前 30 帧等自动曝光稳定
3. `STAGE 2/3` **别把手放进画面** → 采集空背景 30 帧
4. `STAGE 3/3` 把手放进 ROI 内**保持不动** → 采集 3×3 九格、共 60 帧肤色样本
5. `STAGE 4/4` 实时识别。12 帧投票窗口里攒够 8 票才确认，30fps 下约 0.3 秒

任意阶段按 `q` 退出；按 `r` 重新采集背景并重新标定肤色。

## 算法流水线

### 路线 A：插件流水线（`main.py`）

```
输入                        处理类插件（顺序即执行顺序，会改变图像数据）
┌──────────────┐   ┌────────────────────────────────────────────────────────────────────┐
│ 图片（循环）  │   │ mirror → color_threshold → mask_cleanup → palm_reconstruct          │
│ 或 2K 摄像头  │──▶│        → hand_recognize → recognize_on_mask / recognize_on_original │──▶ imshow
│ 或 视频文件   │   └────────────────────────────────────────────────────────────────────┘   1280×720
└──────────────┘                          │
                    hand_recognize 里同时算出 │  掌心 C、手掌尺度 R、手腕、指尖、指缝
                                          │  → 分类出数字手势（结果存进 state.flags）
                                          ▼  绘制类插件（最后执行，只叠标注，不改变数据）
                                    roi_boundary → info_overlay
```

**六层插件的职责：**

| 插件名 | 职责 | 关键点 |
|---|---|---|
| `mirror` | 水平镜像 | 内置插件；图片模式默认关闭（照片本身就是真实方向） |
| `color_threshold` | YCbCr 的 `Cr`/`Cb`/`Y` 三重区间二值化 | 亮度 `Y` 与色度 `Cr`/`Cb` 解耦 → 判"是什么颜色"不受明暗影响 |
| `mask_cleanup` | 小核开运算 + **双门槛**面积过滤 + **只填内部孔洞** | 补洞用 floodFill 从边界找外部背景，**不用闭运算**（闭运算会粘手指） |
| `palm_reconstruct` | 从掌心核心做**颜色约束重建** | 基准 `(Cr0,Cb0,Y0)` 每帧自算，不写死绝对值 → 光照/肤色变了不抖 |
| `hand_recognize` | 截前臂 → 找指尖 → 找指缝 | 只计算不绘制；结果存进 `state.flags` |
| `recognize_on_mask` / `_original` | 把同一份识别结果画在掩膜上 / 原图上 | 两份绘制插件共用一份计算结果 |
| `roi_boundary` | 画真正生效的 ROI 边界 + **触边告警** | 故意**不检查 bottom 边**：小臂从下方入画，查了就永远告警 |
| `gray_threshold` | 灰度上下双阈值 | **已停用**，注册着但代码保留（实测可分性太差，见附录） |

### 手势分类（路线 A）

分类结果**完全由图像算出来**，代码里没有任何按文件名/按张号查表的映射。用的是两个特征：

#### 特征 ①：伸出手指的**根数** `n` —— 主特征

这个选择是**刻意**的，因为它让 **`3` 的两种比法自动归为一类**：

```
gesture_03 = 食指 + 中指 + 无名指   -> 3 根
gesture_33 = 拇指 + 食指 + 中指     -> 3 根
                        ↓
              根数都是 3 -> 零特判自然合并
```

> 反过来说：如果主特征选"哪几根手指"，反而会把 `3` 和 `33` 拆成两类。**这是需求决定设计。**

#### 特征 ②：每根手指**偏离掌轴多少度** —— 用来认拇指

数字 `6` 是"点赞"= **只伸拇指**，数字 `1` 是"只伸食指"，**两者都是 1 根手指**，光数根数分不开。所以要比"这根手指偏不偏"：

| 手指 | 实测偏离角（相对掌轴"朝上"方向） |
|---|---|
| 食指 / 中指 / 无名指 | **2° ~ 18°**（沿掌轴朝上） |
| **拇指** / 小指 | **37° ~ 60°**（侧向） |

两组之间在 37°~49° 有空隙，门槛取 **45°**，两边都留了余量。

#### 判定表

| 伸出手指数 `n` | 附加条件 | 判为 | 说明 |
|---|---|---|---|
| 0 | — | `0` | 握拳 |
| 1 | 偏离掌轴 > 45° | `6` | 点赞（是拇指不是食指）|
| 1 | 否则 | `1` | 只伸食指 |
| 2 | 没有侧向手指 | `2` | 剪刀（食指+中指）|
| 2 | 有一根侧向 | `8` | 手枪（拇指+食指）|
| 2 | 两根都侧向 | `?` | 拇指+小指，不在当前手势集里，如实说不认识 |
| 3 | — | `3` | **`3` 和 `33` 都落这里** |
| 4 | — | `4` | |
| ≥5 | — | `5` | |

**前提**：手指数本身必须准。这是靠"**凸出长度**"判据保证的（见下面"踩坑记录"第 12 条），实测把正确率从 4/9 提到 8/9，再配合"针状毛刺"过滤到 10/11。

#### 实测结果（20 张素材）

| 分组 | 张数 | 分类正确 |
|---|---|---|
| 干净白背景 | 11 | **11** |
| 斑驳背景 | 9 | **9** |
| **合计** | **20** | **20 / 20** |

每对手势两批判出来的数字完全一致 —— 包括第二组**手在画面里大了 20%~74%** 的情况下，说明"所有长度阈值按 `R` 归一化"这条路是对的。

### 路线 B：状态机（`solution.py`）

```
STAGE 0/3  初始化
  └─ 建窗口 → 打开摄像头
        │
        ▼
STAGE 1/3  摄像头预热（丢弃 30 帧，等自动曝光稳定）
        │
        ▼
STAGE 2/3  背景采集（一次性，按 r 可整体重做）
  └─ 空背景 30 帧 → 求平均背景
        │
        ▼
STAGE 3/3  肤色标定
  └─ ROI 内 3×3 九格 × 60 帧 → 要求 ≥500 样本
         → (Y, Cr, Cb) 均值 / 协方差 → 马氏距离阈值 9.0
         + HSV 分位数边界（2% ~ 98%）+ 饱和度 / 亮度硬下限
        │
        ▼
STAGE 4/4  实时识别（逐帧）
  ROI 裁切
    → 背景差分 ⊕ 肤色马氏距离 → 形态学 / 面积筛选 / 上一帧质心跟踪 → 分割掩膜
    → 距离变换求掌心中心 C 与手掌尺度 R
    → 估计手腕 → 构造掌轴 → 前臂截断（去掉 C 下方超过 1.5R 的部分）
    → 轮廓 / 凸包 / 凸缺陷 / 骨架细化 / 骨架端点
    → 多尺度曲率找指尖 + 薄部件抑制 → 指缝检测 → 去重与合并
    → extract_hand_features
    → classify_open_five      硬条件（全过）+ 7 项加权置信度 ≥ 0.60
    → update_stable_state     12 帧滑窗投票：≥8 票且平均置信度 ≥0.65 才确认
    → draw_debug_view → imshow
```

**`classify_open_five` 的硬条件**（任一不满足直接判 `UNKNOWN`，平均分不能补偿）：

- 指尖数 **恰好 5**，指缝数 **恰好 4**
- 实心度（轮廓面积 / 凸包面积）∈ **[0.55, 0.90]**
- 每个指尖到掌心距离 **≥ 1.35 R**
- 至少 1 个指尖到达掌上方区域（局部纵坐标 ≤ −0.8 R）
- 指尖横向跨度 **≥ 2 R**，且必须**横跨掌心两侧**
- 7 项加权得分（指尖 / 指缝 / 实心度 / 跨度 / 指长 / 掩膜质量 / 上方占比，权重 `0.15×5 + 0.125×2 = 1.0`）加权和 ≥ **0.60**

## 关键设计决策与踩坑记录

这一节是这个仓库最有价值的部分 —— 都是实际调试中撞出来的结论。

### 1. 为什么选 YCbCr，而不是灰度或 HSV

灰度把"亮度"和"颜色"揉在一个通道里，**手和米白背景布在灰度上直接重叠**（手 133~181，布 143~205），单靠灰度区间切不开。实测可分性：

| 判据 | 可分性 d′ | 结论 |
|---|---|---|
| 灰度 | **0.74** | 基本没用 |
| **Cr / Cb 色度** | **1.45** | 静态图像里最好的判据 |

而 Cr 和 Cb **各自都能独立把布挡掉**（手 Cb≈118~123 vs 布 129~131；手 Cr≈136~148 vs 布 124~126），相当于双重保险。更重要的是阴影主要改 `Y`、基本不改 `Cr`/`Cb` —— 这正是它能救"手上自阴影导致掩膜出洞"的原因。

### 2. 通道顺序的坑

`cv2.COLOR_BGR2YCrCb` 返回的三通道是 **`Y, Cr, Cb`**。函数名写的是 `YCrCb`，但第 1 个通道是 `Y`、第 2 个是 `Cr`、第 3 个是 `Cb`。取反了阈值就完全不工作，而且报错都没有。

### 3. 面积过滤为什么要"双门槛"

实测最大的噪声块是 **ROI 面积的 1.7%**（画面左下角键鼠那片）。只用绝对百分比门槛的话：调到 0.5% 清不掉，调到 3% 手小一点就被误杀。所以加第二道**相对门槛**——"比最大连通域小得多就丢"，天然随手的大小自适应，也不怕手指被分成两块时误杀。

### 4. 补洞用 floodFill，不用闭运算

闭运算在补洞的同时会**把相邻手指粘起来**，直接毁掉指缝检测。正确做法是从图像边界 `floodFill` 找出真正的"外部背景"，剩下的空洞才是内部洞，只补这些 —— 完全不动外轮廓。

### 5. 掌心重建的基准每帧自算

`palm_reconstruct` 的判据全部是**相对掌心核心** `(Cr0, Cb0, Y0)` 的容差，不是写死的绝对阈值。写死绝对值才会抖：灯一变，同一个像素时进时出，掩膜边缘就会闪烁。基准跟着每帧变 → 视频里稳定。

### 6. 处理类插件必须先执行，绘制类插件必须最后执行

绘制类插件画上去的标注（ROI 框、信息叠加）如果排在处理插件之前，会被后续的二值化当成图像内容吃掉 —— 表现就是"按 `d` / 按 `r` 画面没反应"。代码注释里明确记着**这个坑踩过一次**。

### 7. 暂停时也必须调用 `waitKey`

主循环把 `cv2.waitKey()` 放在 `if not paused` **外面**。否则暂停后界面不再泵事件，按键彻底没反应 —— 表现就是"暂停像死机"。暂停时窗口仍保留最后一帧。

### 8. 图片源必须每次返回拷贝

插件约定允许"就地修改 frame"。如果 `ImageSource.read()` 反复交出同一个数组，第一帧画上去的叠加层会残留到第二帧，镜像插件还会把上一次的结果再翻一次。所以每次 `read()` 都返回 `.copy()`。

### 9. 触边检查故意不查下边

手举在身前时小臂是从画面下方伸进来的。如果连 `bottom` 边一起检查，小臂一出画面就永远告警，反而失去意义。所以 `ROI_CHECK_EDGES = ("left", "right", "top")`。

### 10. 实心度阈值是自己实测的，不是文献值

一开始抄了文献的"张开 0.5~0.65"，**实测完全对不上**。用合成姿态重新量：

| 姿态 | 实心度（轮廓面积 / 凸包面积） |
|---|---|
| 五指张开 | **0.69 ~ 0.70** |
| 五指并拢 | 0.78 |
| 握拳 | 0.88 |

验证过是**单调**的，方向正确。换环境/换人建议重新量一遍。

### 11. 掩膜模式下 ROI 外强制擦黑

`roi_boundary` 插件在掩膜模式下会把 ROI 之外的像素一律 `bitwise_and` 归零，让"ROI 外全黑"**结构性成立**，以后再加标注也不会破坏它。但**必须只对掩膜做**：模式 1 是原图，把外面擦黑它就不是原图了（写单测时踩到过，6.4M 像素对不上）。

### 12. 单一距离门槛两头不讨好 —— 改用"凸出长度"

判断"这是不是一根手指"最初只看**指尖到掌心的距离**。这条路走不通，因为两类东西在**同一维上重叠**：

| 想要的效果 | 需要的门槛 |
|---|---|
| 排掉拳头的**指节凸起**（距掌心 1.26~1.33 R） | 门槛要 **≥ 1.6 R** |
| 保住**很短的小指**真指尖（可能只有 1.4 R） | 门槛要 **≤ 1.4 R** |

**矛盾。** 实测手指数正确率卡在 4/9。

解法是换一个**正交**的量 —— **凸出长度**：从指尖沿直线朝掌心走，量到"内部厚度 ≥ 0.45 R"（= 进入掌区）为止的距离。

| 类型 | 实测凸出长度 |
|---|---|
| 假（指节凸起等） | 0.67 ~ 1.33 R |
| **真手指（含很短的小指）** | **1.53 ~ 2.33 R** |

中间有干净的空隙 → 门槛取 **1.45 R**（1.35~1.50 是稳定平台）。手指数正确率从 4/9 提到 8/9。

### 13. 指缝不能"按位置去重"

指缝是**每一对相邻指尖**之间取一个谷点。曾经按 0.35 R 做位置去重，结果把中间两条相邻指缝（实测只差 **20.8 px**）当成同一条给合并了 —— **5 指只剩 3 条缝**，连带指根位置全乱。

但**这个去重本身就是多余的**：每条缝来自**不同的相邻指尖对**，用的是轮廓上**互不重叠的弧段**，结构上不可能重复。去掉后立刻恢复 4 条缝。

### 14. 前臂截断必须是"半平面"，否则会削平指尖

截断前臂的多边形，我一开始把边距写成 `4R`。结果多边形在**手指方向**也只延伸了 594 px，而指尖离截断线有 **601 px** —— **整片指尖被削平了**，切口上的毛刺被当成 4 个"假指尖"。

**判据**：手指区每行游程数在 y=330~390 全是 0，y=400 才突然冒出 3~5 个 —— 一看就是被切了。

修法：沿两个方向都延伸到远大于图像尺寸，等价于**半平面**。

### 15. 闭运算不能用来"补掩膜上的口子" —— 没有安全区间

掩膜有时会被割出一道从边界进去的口子（重建那步按颜色筛，可能把掌区切掉一块）。直觉是用闭运算合上它。**实测不行**：

| 核大小 | 效果 |
|---|---|
| 21 | ❌ `shou1` 手指开始被粘住（5→4）|
| 25 | ✅ 口子合上 **但** ❌ 手指也被粘 |

**"合口子要 25、粘手指从 21 就开始" —— 两个区间重叠，没有安全值。**

### 16. 于是把两个需求解耦：闭运算**只用来估掌心**

真正的矛盾是**两个需求打架**：

| 需求 | 要什么 |
|---|---|
| 估掌心 `R`（最大内切圆） | 手掌要**实心** → 闭运算帮忙 |
| 找指尖/指缝 | 指缝要**锋利** → 闭运算坏事儿 |

所以**别用同一张掩膜**：闭运算只作用在**一份副本**上、专门估掌心；**指尖检测仍用原始掩膜，一点没动**。

实测（20 张素材）：核在 **11~41** 这个很宽的范围内**手指数 0 错误**；对健康图几乎无扰动（`R` 只差 −5%~+1%），只把坏的那张修好（`gesture_03_busy` 的 `R` 从 101.5 恢复到 **162.6**，+60%）。

### 17. 核大小不能按 `R` 算 —— 会陷入鸡生蛋

第 16 条那版实现，我一开始把核大小定为 `0.13 × R`。**结果没修好**（`R` 只从 101.5 到 103.0）。原因：

> **`R` 本身就是被低估的那个量**（口子让最大内切圆只能塞进半块掌）。拿错的 `R` 去定核 → 核不够大 → 口子合不上 → `R` 还是小的。**死循环。**
> 实测：按 `R` 算核只有 **12**（合不上），合上需要 **25**。

改成按**掩膜面积**算（`0.13 × √(面积/π)`，即等效半径）：面积几乎不受割口影响，是稳的尺度 → 得到核 **29**，`R` 恢复到 162.6 ✓

> 教训：**别用一个"正在被修正的量"去决定修正的力度。**

### 18. `cv2.putText` 画不了中文

`cv2.putText` 用的是 Hershey 矢量字体，**只支持 ASCII**。拿它画"点赞"只会得到一串问号/方框 —— 这跟字号、位置都无关，是根本不支持。

解法：借 **PIL + 中文字体**（按顺序找微软雅黑/黑体/宋体/等线，全找不到才退回英文）。

⚠️ **性能坑**：如果对整幅 1920×1440 反复做 BGR↔RGB 转换，每行要好几毫秒，一屏七八行就吃掉几十毫秒。所以**只转换文字覆盖的那一小块区域**，而且整个面板只做**一次** PIL 往返。

⚠️ **可读性坑**：小字号中文笔画密，8 方向黑描边会把字内空隙填满、**糊成一团黑块**。所以小字号改用"半透明底衬 + 不描边"，大字号（≥22 px）才用描边。

### 19. 暂停时按 `n` 换图，画面纹丝不动

主循环原来是这样的：

```python
if not state.paused:          # ← 暂停时整块被跳过
    ... 取帧 / 处理 / imshow ...
key = cv2.waitKey(...)
if key == 'n':
    image_source.step(+1)     # 图真的换了，终端也打印了新文件名
    continue                  # 但永远走不到 imshow -> 画面一次都不重绘
```

表现就是：**终端说文件名变了、画面没变化**。更糟的是因为不重绘，连 `PAUSED` 标记也画不出来，**用户分不清是"暂停"还是"卡死"**。

修两处：暂停时**也重绘**（画一个居中的 `PAUSED` 标记）；按 `n/p/R` 时置一个 `refresh_requested`，**即使暂停也强制处理并显示一帧**。

### 20. 针状毛刺会被当成指尖

轮廓上会出现 **1~2 像素的针状凸起**。它的夹角只有 **1°**、内部厚度 **0.00**，而真指尖是"圆帽"（夹角 46~58°、厚度 0.08~0.19）。加一条判据：**夹角和厚度同时极端小才拒绝**（保守写法，不误伤真正尖锐的指尖）。

### 21. 别把训练集当验证集

有一批图我看了半天觉得"表现很好"，后来才发现**那 9 张其实都是同一个手势**（五指张开），只是背景和距离不同。所谓"多次验证"根本没验证到别的类别。

**教训**：拿到素材第一件事是先确认**类别是否真的有区别**，别拿一堆同类别样本当交叉验证。

### 加一个手势要改哪

1. 拍一张新手势的照片，按 `gesture_<两位数编号>.jpg` 命名放进仓库根目录
2. 在 `main.py` 的 `GESTURE_SAMPLES` 里加一行 `(编号, "说明", ("文件名",))` —— **`IMAGE_FILES` 会自动跟着变**
3. 在 `plugins.py` 的 `classify_gesture()` 里加对应的判定分支

> `classify_gesture()` 目前是**规则式**的（根数 + 偏离角），加手势就是加规则。如果想省掉手写规则，可以把特征向量 `(手指数, 极角跨度, 实心度, 指长均值)` 交给最近邻/阈值分类器 —— 特征已经在 `state.flags["recognize"]` 里算好了。

### 调参原则

- **每一对阈值都要求下限 ≤ 上限**；写反了程序会自动交换并打印提示（不会出现"整幅全黑还找不到原因"）
- **几何阈值尽量按手掌尺度 `R` 或 ROI 面积归一化**，只有形态学核尺寸和少量安全边界用固定像素 —— 这样拍摄距离变化时不用重新调
- **想更严（少误检）**：抬 `CR_LOW`、压 `CB_HIGH`、收紧 `MIN_SOLIDITY`
- **想更松（少漏检）**：反向操作。但注意 —— 放宽阈值**买不到多少完整性**（见附录的 Cr 扫描表），**真正让掩膜变干净要靠清理插件**
- 现场调参建议配 `cv2.createTrackbar` 滑动条，别靠脑补数字

### 两个关键判据的"真假分离度"

**① 凸出长度**（判"这是不是一根手指"，见踩坑 #12）：

| 类型 | 凸出长度 |
|---|---|
| 假（指节凸起等） | 0.67 ~ **1.33** R |
| **真手指（含很短的小指）** | **1.53** ~ 2.33 R |

门槛取 **1.45 R**。中间空隙 1.33↔1.53，两边都有余量。

**② 偏离掌轴的角度**（判"这根是不是拇指"，见[手势分类](#手势分类路线-a)）：

| 手指 | 偏离角 |
|---|---|
| 食指 / 中指 / 无名指 | **2° ~ 18°** |
| 拇指 / 小指 | **37° ~ 60°** |

门槛取 **45°**。

### 手指数正确率怎么从 4/9 提到 8/9

|---|---|

| 只看距离门槛 `1.40 R` | 7 / 9 |
| **改用凸出长度 `1.45 R`** | **8 / 9** |

|---|---|---|---|
| `gesture_03_busy` | 101.5 | **162.6** | **+60.2%** ← 掩膜被割口子，补救生效 |

> 只有坏的那张大幅变化，说明这个修正**不扰动健康样本**。

### 两批素材的尺度差异（验证尺度不变性）

| 手势 | `R` 干净 → 斑驳 | 手占画面高度 |
|---|---|---|
| 握拳 | 150 → **262**（+74%） | 20.9% → 36.3% |
| 三指（中式） | 162 → **219**（+35%） | 22.5% → 30.4% |
| 只伸食指 | 149 → 191（+28%） | 20.7% → 26.5% |

### 性能

| 分辨率 | 整条链耗时 | 折合帧率 |
|---|---|---|
| 4096×3072（相机原图） | 360 ~ 470 ms | ~2.5 fps |
| **1920×1440**（自动降采样后） | **62 ~ 72 ms** | **~14 fps** |
| 1280×720 | ~58 ms | ~17 fps |

> **注意 1280×720 只比 1920×1440 快一点点** —— 说明有一大块**固定开销**（Python 层的多次连通域标记、HUD 的 PIL 渲染等），不是像素数在主导。**光靠降分辨率提升有限**，真要提帧率得从算法层砍（比如把处理限制在小 ROI 里）。
>
> 另外 `main.py` 里的**图片降采样是在载入时做一次**的（`ImageSource.load()`），不是每帧做。

`plugins.py` 按功能分七部分，每部分的配置都在文件开头、顺序排列：

| 部分 | 内容 |
|---|---|
| 一 | ROI 配置（限制识别区域）|
| 二 | 灰度双阈值（**已停用**，代码保留）|
| 三 | 颜色阈值（YCbCr 的 `Cr`/`Cb`/`Y`）|
| 四 | 掩膜清理（开运算 + 面积过滤 + 填洞）|
| 五 | 掌心重建（模式 4）+ **掌心估计的稳健化** |
| 六 | 识别骨架（模式 5/6）：截前臂 → 指尖 → 指缝 → 指根 |
| 七 | **手势分类**（数字）|

> **注**：本仓库**只提交代码，不含任何图片素材**（`.gitignore` 并未忽略图片，是就没有提交）。使用图片模式前请按前面[快速开始](#快速开始)里的命名表自行放入。摄像头模式与视频模式不需要素材。

### 想扩展？插件机制是开放的

在同目录新建 `plugins.py`（或修改现有的），定义 `register(api)` 即可接入，**主程序一行都不用改**：

```python
def register(api):
    api.add("my_step", my_step, enabled=True)
```

插件函数签名约定：

```python
def my_step(frame: np.ndarray, state: FrameState) -> np.ndarray | None:
    """
    frame : 插件工作帧（默认是原图整帧，是一份拷贝，可放心就地修改）
    state : 本帧共享状态（帧号/时间/FPS/原始帧/裁切区/flags 自由字典）
    返回 None 表示丢弃本帧，主循环会跳过后续插件与显示（用于省算力）
    """
```

新增显示模式：在 `main.py` 的 `VIEW_MODES` 里追加一项、分配一个没被占用的数字键即可。

## 已知限制与 Roadmap

**当前限制：**

- ❌ **`main.py` 没有时序投票** —— 逐帧独立判定，手一动或光照一抖，相邻帧的 `GESTURE` 就会来回跳。**这是上视频前最该补的一块**（`solution.py` 里已有现成的 12 帧投票实现可以搬）
- ❌ **每个手势只有单张样本** —— 阈值是在这 20 张上实测标定的，**还没验证过跨角度 / 跨距离 / 跨人**。所以 20/20 只是"在这批数据上对"，**不等于泛化能力**
- ❌ `main.py` 的图片模式需要自备素材；仓库不含示例图片
- ❌ 不认的手势只输出 `?`，没有"最接近的候选"或置信度
- ❌ `solution.py` 使用固定 ROI，手移出 ROI 即丢失目标（无跟踪）
- ⚠️ `6` 的判定依赖"拇指是侧向手指"这个几何特征；**小指也在 45° 门槛附近摇摆**（实测 37°~52°），目前用不到，但以后要认"拇指+小指"类手势时需要单独处理
- ⚠️ 实心度等阈值在同一环境下实测标定，换环境建议重新测量

## 开发过程中的自测方法（可复用）

这个仓库的每次改动都配了可复现的自测脚本，值得记一下做法：

| 场景 | 做法 |
|---|---|
| 不想开窗口测主循环 | 把 `cv2.imshow` / `waitKey` / `namedWindow` 等**全部打桩**，`waitKey` 按脚本吐按键，`imshow` 把帧存盘后肉眼看 |
| ⚠️ 打桩 `_prepare_window` | 它内部**自己会调 3 次 `waitKey`**，不打掉会把按键脚本提前吃掉（我踩过，导致结论完全错）|
| 数据集的回归测试 | 遍历 `GESTURE_SAMPLES`，逐张跑完整链，打印"真值 vs 判定 vs 特征"，一眼看出哪张退化 |
| 参数扫描 | 固定其他量、只扫一个阈值，输出成表格找"稳定平台"，而不是取单点最优 |
| 验证"方向对不对"时没有真实样本 | 用**合成姿态**（形态学闭运算模拟并拢、掌核模拟握拳）验证特征单调性 |
