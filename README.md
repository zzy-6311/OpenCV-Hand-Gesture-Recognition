**纯传统计算机视觉（classical computer vision）的手势识别 —— 不依赖 CNN、MediaPipe、任何深度学习运行时或云端服务。**

全部算法只用 `opencv-python` + `numpy` + Python 标准库手写：YCbCr 色度阈值分割、**场景色度自校准**、颜色约束重建、距离变换找掌心与手掌尺度、轮廓距离剖面找指尖、多尺度曲率、凸缺陷、几何特征分类。

## 这个项目干了什么

**从摄像头/图片里认出人比的手势数字。**

具体说：输入一帧画面 → 把"像皮肤"的部分切出来 → 找出手掌在哪、手掌有多大（作为量长度的尺子）→ 沿着手的轮廓找出每根伸出的手指 → 数出根数、看每根手指偏不偏 → 判出这是哪个手势。

| 能力 | 说明 |
|---|---|
| **识别范围** | 中国式数字手势 `0` `1` `2` `3` `4` `5` `6` `8`，外加自定义的 **`ye`（耶）**，共 **9 类** |
| **同数字的多种比法自动归一** | `3`：食+中+无名 和 拇+食+中 都判 `3`；`6`：只伸拇指 和 拇+小指 都判 `6` |
| **不需要标定** | 换背景、换光照都自动适应（场景色度自校准）|
| **横竖画幅都行** | ROI 按画面短边自适应；显示等比缩放，不会被拉变形 |
| **三种输入源** | 磁盘图片循环 / 摄像头 / 视频文件 |
| **极端轻量** | 只要 `opencv-python` + `numpy`，无模型文件、无 GPU、无网络请求 |

**实测成绩**：28 张素材（三种背景/光照 × 横竖两种画幅 × 两档拍摄距离）**28/28 全对**，其中老的两批 18 张一张都没退化。

> 分类结果**完全由图像计算得出** —— 代码里没有任何"按文件名/按张号查表"的映射。
>
> **每个手势的样本仍然偏少**（数字类 1~3 张、`ye` 只有 1 张），所以 28/28 只说明"在这批数据上对"，**不等于泛化能力**。

## 项目定位与能力边界

**先说实话，避免误解：**

| 项目名说的是 | 实际目前做到的 |
|---|---|
| Hand Gesture Recognition（手势识别） | 能判出 `0/1/2/3/4/5/6/8` 共 8 类数字手势，外加自定义的 `ye`（耶），**共 9 类输出** |
| 通用手势库 | 不认的手势会输出 `?`（未知）而不是乱猜 |
| 开箱即用 | 不是。需要自备图片素材，或改用摄像头/视频模式 |

- ✅ **分类目标**：中国式数字手势 `0`(握拳) `1` `2`(剪刀) `3` `4` `5`(五指张开) `6`(点赞/只伸拇指) `8`(手枪/拇指+食指)，外加 **`ye`（食指+小指+拇指，大张开）**
- ✅ **同一个数字的多种比法会自动归为一类**（原理见[手势分类](#手势分类)）：
  - `3`：`食指+中指+无名指` 和 `拇指+食指+中指` 都判 `3`
  - `6`：`只伸拇指`（点赞）和 `拇指+小指` 都判 `6`
- ✅ 极端轻量：无模型文件、无 GPU、无网络请求，CPU 实时
- ✅ 算法完全透明可调：每个阈值都有物理含义，而且**代码注释里都写明了实测依据**（当初为什么取这个值、试过哪些值、数据是多少）
- ✅ **颜色阈值会跟着光照自己调**（见[场景色度自校准](#场景色度自校准第-1-层里的关键一环)），不需要换场景就重调参数
- ✅ **横竖画幅都支持**：ROI 按画面短边自适应，显示等比缩放不会变形
- ⚠️ **面向室内场景**：白板 / 斑驳桌面 / 印花床单 三种背景实测都通过，但**背景色和肤色本身重叠时无解**（调阈值救不了，因为两者在颜色空间里本来就有交叠）
- ⚠️ 每个手势样本仍然偏少，**还没有做过跨角度 / 跨人的验证**

这是一个**算法研究与调参用**的项目，不是开箱即用的通用手势识别 SDK。

> **说明**：早年还有一条"背景差分 + 马氏距离肤色模型"的备选路线（需要一次性标定、只识别数字 5），因为必须固定背景、和"随时换背景测试"的目标冲突，**已经删除**。其中两项设计（**时序投票策略**、**置信度打分**）在本地开发笔记里留有摘录，是以后要做时序投票时的参考。

## 快速开始

### ⚠️ 第一次运行 `main.py` 之前必读

本仓库**只提交代码，不提交图片素材**（素材是私人拍摄的照片）。而 `main.py` 默认走图片模式，`IMAGE_FILES` 由 `GESTURE_SAMPLES` 自动展平出 **30 个文件名**。

**素材放在 `data/` 子目录里**（由 `main.py` 开头的 `DATA_DIR = "data"` 决定）：

```python
DATA_DIR = "data"
SOURCE = "image"
GESTURE_SAMPLES = (
    (0,  "握拳",       ("gesture_00.jpg", "gesture_00_busy.jpg", "gesture_00_s3.jpg")),
    ...
)
```

> 表里写的是**裸文件名**，路径前缀在解析时统一拼 —— **要改素材位置只动 `DATA_DIR` 一个地方**，表里的文件名不用动。
> 写成 `DATA_DIR = ""` 就退回"素材和代码放同一个目录"的老做法。

**直接 `python main.py` 会打印"图片模式下一张可用图片都没有"并退出**（返回码 1），报错里会**直接把找素材的目录路径打出来**。三个办法任选：

**办法 1：改用摄像头模式（推荐先跑通这条）**

```python
# main.py 配置区
SOURCE = "camera"          # "image" / "camera" / "video"
```

```bash
python main.py
```

**办法 2：改用视频文件模式**

```python
SOURCE = "video"
VIDEO_FILE = "my_gesture.mp4"   # 相对 DATA_DIR，也可写绝对路径
VIDEO_LOOP = True               # 播完循环；False = 播完自动退出
```

**办法 3：按下面的命名把图片放进 `data/`**

命名规则是 `gesture_<标签>[_<场景>].jpg`。目前有**三组场景**（同一个手势在不同背景/光照下各拍一次）：

| 后缀 | 场景 | 画幅 |
|---|---|---|
| （无）| 白板干净背景、明亮白光 | 横幅 4096×3072 |
| `_busy` | 斑驳桌面背景、明亮（手离镜头更近）| 横幅 4096×3072 |
| `_s3` | 印花床单背景 + 暗暖光、手在画面左侧 | **竖幅 2304×4096** |

| 标签 | 手势 | 分类结果 |
|---|---|---|
| `00` | 握拳 | `0` |
| `01` | 只伸食指 | `1` |
| `02` | 食指+中指（剪刀）| `2` |
| `03` | 三指（西式：食+中+无名）| `3` |
| `04` | 四指 | `4` |
| `05` | 五指张开 | `5` |
| `06` | 点赞（只伸拇指）| `6` |
| `08` | 手枪（拇指+食指）| `8` |
| `33` | 三指（中式：拇+食+中）| **也判 `3`** |
| `66` | 六（拇指+小指）| **也判 `6`** |
| `ye` | 耶（食+小指+拇，大张开）| `ye` |

> **`33` 代表数字 `3`、`66` 代表数字 `6`，不是数字 33 / 66。** 它们是同一个数字的**不同比法**，
> 分类器会自动归为一类（见[手势分类](#手势分类)）。
>
> **`ye` 只有 s3 那一张**（`gesture_ye.jpg`）。
>
> 少放几张不会报错，`resolve_image_paths()` 会打印跳过哪些、继续跑剩下的。
> 图片载入时会自动缩到 2K 以内（`IMAGE_MAX_WIDTH/HEIGHT`），**严格保持宽高比**，所以 4096×3072 的相机原图可以直接丢进来。

> **另有一个 `data/不能识别/` 子目录**，里面放目前识别不了的样张（附 `说明.txt` 写明原因）。
> 它不会被 `main.py` 加载，也不在 `GESTURE_SAMPLES` 里。

图片模式下会把**同一张图循环反复处理**，方便你一边看叠加结果一边按 `1`~`6` 切换中间层、按 `n`/`p` 换图、按 `r` 对比 ROI 开关效果。

## 算法原理与流程

### 整体流程

```
输入                        处理类插件（顺序即执行顺序，会改变图像数据）
┌──────────────┐   ┌────────────────────────────────────────────────────────────────────┐
│ 图片（循环）  │   │ mirror → color_threshold → mask_cleanup → palm_reconstruct          │
│ 或 2K 摄像头  │──▶│        → hand_recognize → recognize_on_mask / recognize_on_original │──▶ imshow
│ 或 视频文件   │   └────────────────────────────────────────────────────────────────────┘   1280×720
└──────────────┘                          │
                    hand_recognize 里同时算出 │  掌心 C、手掌尺度 R、手腕、指尖、指缝
                                          │  → 分类出数字手势（结果存进 state.flags）
                                          ▼  绘制类插件（最后执行，只叠标注，不改变数据）
                                    roi_boundary → info_overlay
```

**八个插件的职责：**

| 插件名 | 职责 | 关键点 |
|---|---|---|
| `mirror` | 水平镜像 | 内置插件；图片模式默认关闭（照片本身就是真实方向） |
| `color_threshold` | YCbCr 的 `Cr`/`Cb`/`Y` 三重区间二值化 | 亮度 `Y` 与色度 `Cr`/`Cb` 解耦 → 判"是什么颜色"不受明暗影响 |
| `mask_cleanup` | 小核开运算 + **双门槛**面积过滤 + **只填内部孔洞** | 补洞用 floodFill 从边界找外部背景，**不用闭运算**（闭运算会粘手指） |
| `palm_reconstruct` | 从掌心核心做**颜色约束重建** | 基准 `(Cr0,Cb0,Y0)` 每帧自算，不写死绝对值 → 光照/肤色变了不抖 |
| `hand_recognize` | 截前臂 → 找指尖 → 找指缝 | 只计算不绘制；结果存进 `state.flags` |
| `recognize_on_mask` / `_original` | 把同一份识别结果画在掩膜上 / 原图上 | 两份绘制插件共用一份计算结果 |
| `roi_boundary` | 画真正生效的 ROI 边界 + **触边告警** | 故意**不检查 bottom 边**：小臂从下方入画，查了就永远告警 |
| `gray_threshold` | 灰度上下双阈值 | **已停用**，注册着但代码保留（实测灰度可分性只有 0.74，色度是 1.45，太差所以不用） |

### 场景色度自校准（第 1 层里的关键一环）

颜色阈值本身是**写死的绝对值**，但**每帧会先按当前场景把整个框平移一下**再切：

```
① 隔 4 行 4 列取样（省时间，约 1/16）
② 算 ROI 内 Cr / Cb 的【中位数】
     · 框里背景占大头、手只占一小块 -> 中位数基本就是背景色
     · 中位数不怕个别高光/阴影（均值会被拽跑）
③ dCr = 本帧背景 Cr 中位 − 127.0      (127.0 = 标定基准，白板场景量出来的)
   dCb = 本帧背景 Cb 中位 − 128.0
④ 夹到 ±22（保险丝，防止估计跑飞）
⑤ 把肤色框的上下限都 +dCr / +dCb
```

**实际走一遍**：

| 场景 | 本帧背景中位 | 偏移量 | 平移后的肤色框 | 原始阈值前景 |
|---|---|---|---|---|
| 白板（基准）| Cr 127 / Cb 128 | **+0 / +0** | 不变 | 12.8% → **12.8%** |
| 斑驳桌面 | Cr 128 / Cb 126 | +1 / −2 | Cr[132,174] | 17.7% → 17.4% |
| **印花+暗光** | **Cr 133 / Cb 121** | **+6 / −7** | **Cr[137,179] Cb[70,121]** | **66% → 30%** |

> **基准场景算出来是 `+0/+0`，框原样不动** —— 这就是它对老场景**零副作用**的原因（白板/斑驳两批一直满分）。

> ⚠️ 估算背景时**故意不用"当前掩膜之外的像素"** —— 那是循环论证：阈值已经糊掉时，
> 被排除在外的只剩画面里最亮的那部分，估出来的平移方向是**反的**。用整个 ROI 的中位数才稳。

> ⚠️ **如果偏移量顶到 ±22 上限**（HUD 上能看到），说明这个场景偏得太多，
> 应该考虑重设基准 `SCENE_BASELINE_CR/CB`。

### 手势分类

分类结果**完全由图像算出来**，代码里没有任何按文件名/按张号查表的映射。用的是三个特征：

#### 特征 ①：伸出手指的**根数** `n` —— 主特征

这个选择是**刻意**的，因为它让 **同一个数字的多种比法自动归为一类**：

```
gesture_03 = 食指 + 中指 + 无名指   -> 3 根
gesture_33 = 拇指 + 食指 + 中指     -> 3 根
gesture_06 = 只伸拇指（点赞）       -> 1 根 ┐
gesture_66 = 拇指 + 小指            -> 2 根 ┘ 6 的两种比法，靠下面的特征合并
                        ↓
              根数相同 -> 零特判自然合并
```

> 反过来说：如果主特征选"哪几根手指"，反而会把 `3` / `33` 拆成两类。**这是需求决定设计。**

#### 特征 ②：每根手指**偏离掌轴多少度** —— 用来认拇指

数字 `6` 是"点赞"= **只伸拇指**，数字 `1` 是"只伸食指"，**两者都是 1 根手指**，光数根数分不开。所以要比"这根手指偏不偏"：

| 手指 | 实测偏离角（相对掌轴"朝上"方向） |
|---|---|
| 食指 / 中指 / 无名指 | **2° ~ 18°**（沿掌轴朝上） |
| **拇指** / 小指 | **37° ~ 60°**（侧向） |

两组之间在 37°~49° 有空隙，门槛取 **45°**，两边都留了余量。

> ⚠️ **小指的偏角本身就在 45° 门槛附近摇摆**（实测 37~52°），所以"侧向手指数"这个特征对**小指**不太稳。
> 需要区分小指时（比如下面的 `ye`）不能只靠它。

#### 特征 ③：手指的**极角跨度** —— 区分"相邻手指"和"隔开手指"

新加的 `ye`（食指+小指+拇指，中指和无名指蜷缩）和 `3` / `33` **手指数完全相同**，光靠①②分不开。
区别在**结构**：`3`/`33` 伸出的是**相邻**手指，`ye` 伸出的是**隔开**的手指。

| 手势 | 伸出哪几根 | 结构 | 极角跨度 |
|---|---|---|---|
| `3`（西式）| 食+中+无名 | 相邻 | 43.5 ~ 47.9° |
| `33`（中式）| 拇+食+中 | 相邻 | 40.4 ~ 45.3° |
| **`ye`** | **食 + 小 + 拇** | **隔开** | **98.3°** |

**跨度差了一倍以上**，门槛取 **70°**。

> ⚠️ 必须带 `n==3` 的前提：五指张开（106~119°）和 `66`（107°）跨度也很大，不限定根数会被误判成 `ye`。

#### 判定表

| 伸出手指数 `n` | 附加条件 | 判为 | 说明 |
|---|---|---|---|
| 0 | — | `0` | 握拳 |
| 1 | 偏离掌轴 > 45° | `6` | 点赞（是拇指不是食指）|
| 1 | 否则 | `1` | 只伸食指 |
| 2 | 没有侧向手指 | `2` | 剪刀（食指+中指）|
| 2 | 有一根侧向 | `8` | 手枪（拇指+食指）|
| 2 | 两根都侧向 | `6` | 拇指+小指（**`6` 的另一种比法**）|
| 3 | 跨度 < 70° | `3` | **`3` 和 `33` 都落这里** |
| 3 | 跨度 ≥ 70° | **`ye`** | **食+小+拇，隔开的手指** |
| 4 | — | `4` | |
| ≥5 | — | `5` | |

> **标签不一定是数字**：`classify_gesture()` 返回什么标签，`GESTURE_SAMPLES` 里就写什么。
> `ye` 返回的 `digit` 就是字符串 `"ye"`（HUD 用 `%s` 格式化，能直接显示）。

**前提**：手指数本身必须准。这是靠"**凸出长度**"判据保证的 —— 只看"指尖到掌心的距离"会因为拳头的指节凸起和很短的小指在同一维上重叠而死锁（实测正确率卡在 4/9），换成凸出长度后提到 8/9，再配合"针状毛刺"过滤到 10/11。

#### 实测结果（28 张素材）

| 分组 | 张数 | 分类正确 |
|---|---|---|
| 干净白背景 | 11 | **11** |
| 斑驳背景 | 9 | **9** |
| **合计** | **20** | **20 / 20** |

同一个标签在三批里判出来的数字完全一致 —— 包括第二组**手在画面里大了 20%~74%** 的情况下，说明"所有长度阈值按 `R` 归一化"这条路是对的。

### 想扩展？插件机制是开放的

在同目录新建 `plugins.py`（或修改现有的），定义 `register(api)` 即可接入，**主程序一行都不用改**：

```python
def register(api):
    api.add("my_step", my_step, enabled=True)
```

插件函数签名约定：

```python
def my_step(frame: np.ndarray, state: FrameState) -> np.ndarray | None:
    """
    frame : 插件工作帧（默认是原图整帧，是一份拷贝，可放心就地修改）
    state : 本帧共享状态（帧号/时间/FPS/原始帧/裁切区/flags 自由字典）
    返回 None 表示丢弃本帧，主循环会跳过后续插件与显示（用于省算力）
    """
```

新增显示模式：在 `main.py` 的 `VIEW_MODES` 里追加一项、分配一个没被占用的数字键即可。

## 已知限制与 Roadmap

**当前限制：**

- ❌ **`main.py` 没有时序投票** —— 逐帧独立判定，手一动或光照一抖，相邻帧的 `GESTURE` 就会来回跳。**这是上视频前最该补的一块**
- ❌ **样本仍然偏少** —— 阈值是在这 28 张上实测标定的，**还没验证过跨角度 / 跨距离 / 跨人**。所以 28/28 只是"在这批数据上对"，**不等于泛化能力**（`ye` 更是只有 1 张，70° 门槛完全是从单张量出来的）
- ❌ **竖幅画面下 HUD 文字变小** —— 显示适配把 810×1440 缩到 405×720（50%），画在画面里的 HUD 也跟着缩一半，底部 17~18px 的小字基本看不清。三个候选方案见下面的 Roadmap
- ❌ **输入仍受 `IMAGE_MAX_*`（2K）限制** —— 想改成"原图输入 + 只算 ROI 区域"（那样既不限制输入分辨率、耗时又可控、ROI 细节还能多一点），但**显示方式要先定**：只显示 ROI 裁切区 / 仍显示整张照片
- ❌ `main.py` 的图片模式需要自备素材；仓库不含示例图片
- ❌ 不认的手势只输出 `?`，没有"最接近的候选"或置信度
- ⚠️ **`ROI_AUTO_TRACK`（自动跟手）默认关闭** —— B 方案到位后再测是 `x1=26 / x3=27 / x5=25`，**非单调 = 不是真实提升**（收敛后 ROI 只挪 ~40px、掩膜没被切，±2 是噪声抖动；而且 s1 的 `gesture_05` 跟踪后会被顶到画面底部夹住）。代码保留，等有更稳的锚点再开
- ⚠️ **背景色和肤色本身重叠时无解** —— 比如 `data/不能识别/gesture_01_s3.jpg`（床单粉色花纹紧贴食指，颜色和肤色撞车，多出一个假指尖）。**调阈值救不了，因为两者在颜色空间里本来就有交叠**
- ⚠️ 实心度等阈值在同一环境下实测标定，换环境建议重新测量

**可以往下做：**

## 开发过程中的自测方法（可复用）

这个仓库的每次改动都配了可复现的自测脚本，值得记一下做法：

| 场景 | 做法 |
|---|---|
| 不想开窗口测主循环 | 把 `cv2.imshow` / `waitKey` / `namedWindow` 等**全部打桩**，`waitKey` 按脚本吐按键，`imshow` 把帧存盘后肉眼看 |
| ⚠️ 打桩 `_prepare_window` | 它内部**自己会调 3 次 `waitKey`**，不打掉会把按键脚本提前吃掉（我踩过，导致结论完全错）|
| 数据集的回归测试 | 遍历 `GESTURE_SAMPLES`，逐张跑完整链，打印"真值 vs 判定 vs 特征"，一眼看出哪张退化 |
| 参数扫描 | 固定其他量、只扫一个阈值，输出成表格找"稳定平台"，而不是取单点最优 |
| 验证"方向对不对"时没有真实样本 | 用**合成姿态**（形态学闭运算模拟并拢、掌核模拟握拳）验证特征单调性 |
